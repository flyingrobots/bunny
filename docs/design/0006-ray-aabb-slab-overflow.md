# 0006 — `ray_intersects_aabb` reports a miss when a slab division overflows

Status: accepted, option (a), implemented in PR #236. Issue: flyingrobots/bunny#211.

The maintainer chose option (a) as a declared contract change. The current contract is described
in `docs/topics/ray-tracing/README.md#general-purpose-ray-aabb-solver` and the rustdoc of
`ray_intersects_aabb`; this note keeps the analysis that led to it. Two details differ from the
sketch below: coordinate differences are widened to `i128` rather than saturated, and on the
overflow path the hit is decided with exact rationals before the bounds are saturated, because
two entries that both saturate to the maximum would otherwise tie and report a false hit. The
differential test the option asked for found no input whose previous `Some` result changes.

## Finding

The defect is real. `RayInterval::update` in `crates/bunny-query/src/ray.rs` computes each slab
distance as `checked_sub(...)?.checked_div(direction)?`. When the quotient does not fit in
Q32.32, `?` makes `ray_intersects_aabb` return `None`, and `bunny_broadphase::intersect_ray`
reads `None` as a miss and skips the node. Reproduced in
`crates/bunny-query/tests/ray_aabb_overflow_tests.rs` and, through a one-leaf BVH, in
`crates/bunny-broadphase/tests/bvh_tests.rs`.

Minimal case: origin `(-5, 0, 0)`, direction `(1, 2^-32, 0)` (passes
`FixedUnitVec3::try_from_unit`), box `[-1, 1]^3`. The ray enters the box at `t = 4` and leaves at
`t = 6`; the function returns `None`. A component of 3 raw units returns the correct
`Some((4, 6))`.

## Which inputs are affected

Two routes to a false miss, both confirmed:

1. **Slab division overflow.** With the origin inside or near a slab of half-width `k` (box
   `[-k, k]`, origin 0 on that axis), `|bound - origin| * 2^32 / d_raw` exceeds `i64::MAX` exactly
   when `d_raw <= 2k`. A test sweeps `k = 1..=64` and `d_raw = 1..=2k+3` and confirms the
   boundary. In real units the component must be below about `2k * 2^-32` of the unit direction,
   that is, smaller than about `k * 4.7e-10`. A distance `D` from the origin to a bound gives
   the same rule with `D` in place of `k`. A negative component behaves the same.
2. **Subtraction overflow.** `bound - origin` overflows when the two differ by 2^31 units or
   more, for example origin x = -1.5e9 and box max x = 7e8. A ray along +x that plainly hits the
   box returns `None`. Only scenes spanning more than half of the Q32.32 range are affected.

False hits: none found. Both routes return `None` only, so the defect produces false misses only.
A genuine miss stays a miss (tested).

### Camera rays

An axis-aligned centre-column ray has an exactly zero component, which takes the
`axis_contains_origin` branch and is correct (control test). A pixel off the axis of a 4K frame
has a component near `1 / 2000`, about 2e6 raw units, far above the threshold for any scene smaller
than about 10^6 units. The defect needs a direction that is *almost* axis-aligned but not exactly:
a component of a few raw units, such as the result of normalising a vector like `(1, 1e-9, 0)`, or
rays generated by repeated rounding. Likely rare for camera rays, possible for secondary rays
(reflections off axis-aligned planes) and for hand-built test rays. I did not measure how often a
renderer produces such directions; that needs a corpus.

## Options

### (a) Saturate the overflowing slab distance (contract change)

Replace `checked_div(...)?` with a saturating division (and `checked_sub` with a saturating or
widened subtraction): an overflowing quotient becomes `i64::MAX` or `i64::MIN` by sign. The
interval logic is then correct for these rays, since the slab spans the whole representable range.

- Output changes for every input in the affected set above: they move from `None` to `Some` (or
  stay `None` when the ray truly misses on another axis). No input that returns `Some` today
  would change, except where a saturated bound now clamps `enter` or `exit`: reviewers should
  confirm this with a differential test against the old function over the non-overflowing set.
- Per the Fidelity Rule this is a contract change: its own issue, a version bump and regenerated
  golden vectors, not a performance PR. The `known_defect_*` tests flip to assert `Some`.
- Cost: one more branch on the overflow path only; the non-overflow path is unchanged.

### (b) Document the limitation and leave the function alone

State on `ray_intersects_aabb` and in the crate README that a component smaller than about
`2 * distance` raw units, or a span over 2^31 units, can report a miss. Callers that cannot
tolerate this must perturb or pre-test directions. I could not verify the claim that the new
`TraceRay::box_entry` (issue #159) avoids the defect: that API is not on `origin/main`, so there
is nothing to test. Zero risk to existing bits; the false miss remains for Lumen's reference scene
if it produces near-axis rays.

### (c) Add a new function and leave this one unchanged

Ship `ray_intersects_aabb_saturating` (a new API with a stated bound, an oracle test against
exact `i128` arithmetic, and golden vectors) and migrate `bunny-broadphase` to it, which is itself
a behaviour change for `intersect_ray` and therefore needs the same decision. Existing callers keep
their bits. This costs two near-identical functions.

## Recommendation

Option (a), as its own contract-change issue. The failure is silent (a ray through a box is
dropped), it is deterministic but wrong, and the fix touches only inputs that are currently wrong.
The Fidelity Rule is about not silently changing correct outputs; here the maintainer should decide
that the old outputs for these inputs were defects. If the maintainer prefers not to change a
released function, (c) is the safe alternative and (b) alone leaves a known false miss in the
traversal path of a renderer that aims at a reproducible image.

## How this was checked

`cargo test --locked -p bunny-query -p bunny-broadphase` inside the `bunny` dev container. No
output bit of any existing function was changed.
